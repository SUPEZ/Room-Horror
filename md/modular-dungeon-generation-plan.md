# План модульной генерации данжа

## Цель

Нужно перейти от одноразовой генерации полного layout к модульной системе, в которой существующие секции данжа не перестраиваются.

Целевая последовательность:

1. При старте создаётся одна `DungeonMasterRoom`.
2. В центре каждой из четырёх сторон комнаты существует выход.
3. Игрок или разработчик выбирает сторону и размер коридора.
4. Генерируется только выбранный коридор.
5. После этого к коридору по отдельным командам добавляются комнаты выбранных типов.
6. Уже построенные комнаты и коридоры не удаляются и не перегенерируются.

Поддерживаемые категории комнат на первом этапе:

- ресурсная;
- боевая;
- пазловая;
- проходная.

## Главное архитектурное решение

PGG следует использовать для создания геометрии отдельной секции, но не как владельца всего жизненного цикла данжа.

Каждая часть становится самостоятельной секцией:

```text
DungeonMasterRoom
├── NorthExit  ── CorridorSection ── RoomSocket ── RoomSection
├── EastExit   ── CorridorSection ── RoomSocket ── RoomSection
├── SouthExit  ── CorridorSection ── RoomSocket ── RoomSection
└── WestExit   ── CorridorSection ── RoomSocket ── RoomSection
```

DungeonMaster-комната после создания считается неизменяемой. Новая секция сначала рассчитывается и проверяется отдельно, затем добавляется в существующий layout.

Принцип операции:

```text
BuildRequest → Plan section → Validate occupancy → Spawn → Register → Update NavMesh
```

Если проверка не прошла, существующий данж не изменяется.

## Единицы размера коридора

Размер коридора лучше задавать не в метрах и не через внутренние параметры `BranchLength Min/Max`, а точным количеством клеток.

Предлагаемый параметр:

```csharp
int LengthInCells;
```

Текущий размер клетки `Warehouse.asset` равен `3 x 1 x 3`, поэтому:

```text
LengthInCells = 5  → приблизительно 15 мировых единиц
LengthInCells = 10 → приблизительно 30 мировых единиц
```

Для MVP:

- ширина коридора: одна клетка;
- длина: настраиваемое целое значение;
- первый участок от DungeonMasterRoom всегда прямой;
- точка начала — клетка сразу за центральным выходом выбранной стороны;
- коридор не может занимать клетки основной комнаты.

В дальнейшем можно добавить режим формы:

```csharp
public enum CorridorLayoutMode
{
    Straight,
    Branched,
    RandomTunnels
}
```

Сначала рекомендуется реализовать `Straight`. Он даёт предсказуемые точки подключения комнат и упрощает проверку коллизий. Случайные ответвления можно вернуть после стабилизации модульного построения.

## Стороны основной комнаты

Направление задаётся относительно transform генератора:

| Сторона | Направление Unity |
|---|---|
| North | `+Z` |
| East | `+X` |
| South | `-Z` |
| West | `-X` |

Каждый выход должен иметь собственное состояние:

```csharp
public enum DungeonExitState
{
    Available,
    Planning,
    CorridorBuilt,
    Blocked
}
```

Это лучше глобального состояния `Completed`: после постройки северного коридора восточный, южный и западный выходы должны оставаться доступными для будущего расширения.

## Сокеты соединения

Соединение секций должно выполняться через явные сокеты, а не через поиск ближайшей комнаты после спавна.

### `DungeonConnectionSocket`

Сокет хранит:

- уникальный ID;
- тип владельца: основная комната, коридор или обычная комната;
- позицию и направление входа;
- размер дверного проёма;
- состояние `Available/Reserved/Occupied`;
- ссылку на подключённую секцию;
- список разрешённых типов секций.

Типы сокетов:

```csharp
public enum DungeonSocketKind
{
    CoreExit,
    CorridorRoom,
    RoomExit
}
```

### Где создаются сокеты

- `DungeonMasterRoom` создаёт четыре `CoreExit`.
- Коридор создаёт `CorridorRoom` вдоль своих сторон.
- Проходная комната может создавать новые `RoomExit` и продолжать ветку.
- Ресурсная, боевая или пазловая комната обычно завершает своё ответвление, но это должно задаваться в конфигурации комнаты.

## Описание типов комнат

Тип комнаты следует хранить в `RoomDefinition : ScriptableObject`, а не кодировать отдельным условием в менеджере.

Предлагаемые данные:

```csharp
public enum DungeonRoomCategory
{
    Resource,
    Combat,
    Puzzle,
    Passage
}
```

`RoomDefinition` должен содержать:

- стабильный ID;
- отображаемое имя;
- `DungeonRoomCategory`;
- prefab или отдельный `FieldSetup`;
- размер footprint в клетках;
- расположение входного сокета;
- дополнительные выходные сокеты;
- минимальную дистанцию от основной комнаты;
- допустимые типы родительских сокетов;
- необходимость обновления NavMesh;
- стоимость строительства, если она появится в геймплее;
- настройки содержимого комнаты.

Примеры:

```text
ResourceRoomDefinition
  Footprint: 3 x 3 cells
  Input sockets: 1
  Output sockets: 0

CombatRoomDefinition
  Footprint: 4 x 4 cells
  Input sockets: 1
  Output sockets: 0..1

PuzzleRoomDefinition
  Footprint: 3 x 4 cells
  Input sockets: 1
  Output sockets: определяется пазлом

PassageRoomDefinition
  Footprint: 2 x 2 cells
  Input sockets: 1
  Output sockets: 1..3
```

## Разделение оболочки и содержимого

Для комнат одинакового размера самый надёжный вариант — разделить:

1. оболочку: пол, стены, дверной проём;
2. содержимое: ресурсы, враги, пазл, декорации.

PGG создаёт оболочку и `RoomContentSocket`. Затем `RuntimeRoomManager` создаёт внутри выбранный content-prefab без обращения к BuildPlanner.

Это позволяет менять ресурсную комнату на другой ресурсный вариант или выбирать набор врагов без генерации геометрии.

Если категории имеют разные размеры или форму, для них используется локальная генерация одной новой `RoomSection`. Она не должна запускать повторный preview всего `DungeonBuildPlanner`.

## Реестр занятого пространства

Нужен единый `DungeonLayoutRegistry`, который становится source of truth для уже построенного runtime-layout.

Он хранит:

- все созданные секции;
- занятые клетки или bounds;
- все свободные и занятые сокеты;
- связь `секция → родительский сокет`;
- seed и параметры каждой операции;
- GameObject и `BuildPlannerReference` созданной секции.

Перед добавлением комнаты менеджер проверяет:

1. Сокет существует и свободен.
2. Вход комнаты совместим с направлением сокета.
3. Footprint не пересекает занятые клетки.
4. Вокруг комнаты остаётся горизонтальный зазор стены `0.3`.
5. Исключение из зазора разрешено только в паре соединяемых дверных проёмов.
6. Комната не перекрывает другие сокеты и NavMesh-critical области.

Проверка должна выполняться до создания GameObject.

## Менеджеры и ответственность

### `ModularDungeonGenerationManager`

Главный координатор:

- создаёт основную комнату;
- принимает команды построения;
- управляет состояниями операций;
- не содержит геометрических алгоритмов;
- отправляет события для UI и сохранения.

### `CorridorSectionGenerator`

- принимает сторону, длину и seed;
- берёт свободный `CoreExit`;
- создаёт коридор от центра выбранной стороны;
- гарантирует прямой входной участок;
- создаёт сокеты для будущих комнат;
- возвращает результат без изменения существующих секций.

### `RoomSectionGenerator`

- принимает `RoomDefinition` и выбранный сокет;
- рассчитывает ориентацию и footprint;
- проверяет размещение через `DungeonLayoutRegistry`;
- создаёт только одну новую комнату;
- создаёт её выходные сокеты.

### `RuntimeRoomManager`

- отвечает за content-prefabs внутри уже существующих оболочек;
- позволяет менять содержимое без PGG;
- при необходимости использует object pool.

### `DungeonNavMeshCoordinator`

- получает событие после успешного добавления секции;
- обновляет NavMesh один раз после завершения операции;
- не запускает обновление во время расчёта или до появления коллайдеров.

## Предлагаемые структуры запросов

```csharp
public readonly struct CorridorBuildRequest
{
    public readonly CorridorSide Side;
    public readonly int LengthInCells;
    public readonly CorridorLayoutMode LayoutMode;
    public readonly int Seed;
}

public readonly struct RoomBuildRequest
{
    public readonly string SocketId;
    public readonly RoomDefinition Definition;
    public readonly int Seed;
}
```

Предлагаемый публичный API:

```csharp
bool TryBuildCorridor(CorridorBuildRequest request);
bool TryAddRoom(RoomBuildRequest request);
bool TrySpawnRoomContent(string sectionId, RoomDefinition definition);
IReadOnlyList<DungeonConnectionSocket> GetAvailableSockets();
```

## Runtime-поток

### Старт игры

```text
Generate DungeonMasterRoom
→ Add four CoreExit sockets
→ Register core footprint
→ State: CoreReady
```

### Постройка коридора

```text
Select side
→ Select LengthInCells
→ Validate corresponding CoreExit
→ Plan corridor section
→ Validate occupancy
→ Spawn corridor
→ Register corridor and its RoomSockets
→ Update NavMesh
```

### Добавление комнаты

```text
Select available RoomSocket
→ Select RoomDefinition
→ Calculate room transform/footprint
→ Validate 0.3 wall clearance
→ Spawn only this room
→ Connect doorway instructions
→ Register new sockets
→ Update NavMesh
```

Ни на одном из этих этапов не вызывается очистка или повторный spawn основной комнаты.

## Изменения относительно текущей реализации

Текущая реализация в `StagedDungeonGenerationManager` строит `SideCorridor` и `ResourceRoomWareHouse` одной операцией и после этого переходит в глобальное состояние `Completed`.

Для целевой системы нужно:

1. Разделить `BuildCorridorAndResourceRooms` на две независимые команды:
   - `BuildCorridor`;
   - `AddRoom`.
2. Убрать обязательную генерацию `ResourceRoomWareHouse` вместе с коридором.
3. Не использовать глобальный `Completed` как запрет дальнейшего расширения.
4. Хранить состояние каждого из четырёх выходов отдельно.
5. После генерации коридора создать набор свободных `CorridorRoom`-сокетов.
6. Добавлять комнаты по одному сокету без вызова `BeginStagedReplanPreviewPreservingGenerated` для существующего layout.
7. Оставить текущий staged API как временный адаптер до перехода на секционные генераторы.

## План интеграции

### Этап 1. Данные и реестр

- Добавить `DungeonSide`, `DungeonRoomCategory`, `CorridorLayoutMode`.
- Добавить `RoomDefinition`.
- Реализовать `DungeonConnectionSocket`.
- Реализовать `DungeonLayoutRegistry`.
- Научить основную комнату регистрировать footprint и четыре выхода.

Результат: существующий данж можно описать как набор секций и соединений.

### Этап 2. Независимый коридор

- Вынести генерацию `SideCorridor` из команды ресурсных комнат.
- Добавить `LengthInCells` в инспектор и runtime API.
- Для MVP заменить случайный tunnel-layout на прямой corridor-layout.
- Привязать начало к центральному выходу выбранной стороны.
- Зарегистрировать corridor footprint и сокеты комнат.

Результат: коридор выбранной длины строится без автоматического создания комнат.

### Этап 3. Добавление одной комнаты

- Создать первую `RoomDefinition` для ресурсной комнаты.
- Добавить выбор свободного сокета.
- Проверять footprint и зазор `0.3` до спавна.
- Создавать только выбранную комнату.
- Подключать дверь и обновлять NavMesh.

Результат: ресурсные комнаты можно добавлять по одной без перегенерации коридора.

### Этап 4. Остальные категории

- Добавить боевую комнату.
- Добавить пазловую комнату.
- Добавить проходную комнату с выходными сокетами.
- Вынести игровое содержимое в отдельные content-prefabs.

Результат: один placement pipeline работает для всех категорий.

### Этап 5. UI и сохранение

- UI выбора стороны и длины коридора.
- UI выбора свободного сокета.
- UI выбора типа комнаты.
- Визуальный preview footprint перед подтверждением.
- Сохранение списка `BuildRequest` и seed каждой секции.
- Восстановление layout в правильном порядке: core → corridors → rooms.

## Что не следует делать

- Не добавлять отдельный большой `DungeonBuildPlanner` для каждой комбинации комнат.
- Не хранить типы комнат в длинном `switch` внутри главного менеджера.
- Не запускать полную перегенерацию при добавлении одной комнаты.
- Не выбирать соединение только через `GetNearestCellTo` после спавна.
- Не разрешать комнате самостоятельно менять уже занятые клетки.
- Не смешивать shell комнаты, gameplay-content и управление layout в одном prefab или менеджере.

## Критерии готовности MVP

- При старте существует ровно одна DungeonMaster-комната.
- На ней есть четыре центральных выхода.
- В инспекторе или UI можно выбрать сторону.
- Можно задать точную длину коридора в клетках.
- Коридор начинается от выбранного центрального выхода.
- Коридор не пересекает основную комнату.
- Постройка одного коридора не блокирует остальные выходы.
- После коридора можно выбрать свободный сокет.
- В сокет можно добавить одну ресурсную комнату.
- При добавлении комнаты основная комната и коридор не пересоздаются.
- Вокруг комнаты сохраняется зазор стены `0.3`, кроме дверного стыка.
- Ошибка размещения не изменяет уже построенный layout.
- NavMesh обновляется после успешного добавления секции.

## Рекомендуемый первый вертикальный срез

Первую реализацию лучше ограничить следующим сценарием:

1. Одна основная комната `5 x 5` клеток.
2. Четыре выхода.
3. Один прямой коридор шириной в одну клетку.
4. Длина коридора выбирается в диапазоне `3..20` клеток.
5. На коридоре создаются сокеты с фиксированным шагом.
6. Доступна одна `ResourceRoomDefinition` фиксированного размера.
7. Ресурсная комната добавляется отдельной кнопкой.
8. После подтверждения тестируются коллизии, двери, зазор `0.3` и NavMesh.

После стабильной работы этого среза можно добавлять случайную форму коридора и остальные типы комнат, не меняя базовую архитектуру.
